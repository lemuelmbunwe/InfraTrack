# InfraTrack --- Database

## 1. Database

**Database:** PostgreSQL\
**Name:** `infratrack`

Laravel migrations are the source of truth for database structure.

## 2. Tables

### `roles`

  Field           Key      Purpose
  --------------- -------- ------------------
  `id`            PK       Role ID
  `name`          UNIQUE   Role name
  `description`            Role description
  `created_at`             
  `updated_at`             

Initial roles: - Admin - Field Inspector - Contractor

### `users`

  Field              Key               Purpose
  ------------------ ----------------- ------------------------
  `id`               PK                User ID
  `name`                               Full name
  `email`            UNIQUE            Login email
  `password`                           Hashed password
  `role_id`          FK → `roles.id`   User role
  `super`                              Super privilege
  `is_active`                          Account status
  `remember_token`                     Laravel authentication
  `created_at`                         
  `updated_at`                         

`super` belongs to the user, not the role.

### `issues`

Stores reported road issues.

Important fields: - `id` --- PK - `reported_by` --- FK → `users.id` -
`photo_path` - `latitude` - `longitude` - `address` (nullable,
geocoded) - `address_text` (nullable, manually entered) - `description`
(nullable) - `severity` - `status` - `reported_at` - timestamps

Severity values are `low`, `medium`, and `high`. New issues start with
status `reported`; current statuses are `reported`, `assigned`,
`in_progress`, and `resolved`. Initial latitude and longitude values are
editable Yaounde test coordinates generated by the frontend, not GPS data.

### `issue_assignments`

Stores issue allocations and preserves contractor reassignment history. In
the planned grouped-assignment model, each allocation also belongs to an
assignment.

Fields: `id` (PK), `assignment_id` (FK → `assignments.id`), `issue_id` (FK →
`issues.id`), `contractor_id` (FK → `users.id`), `assigned_by` (FK →
`users.id`), `assigned_at`, `unassigned_at` (nullable), and timestamps.

Only an assignment with `unassigned_at IS NULL` is current.

An issue has at most one current allocation. Reassignment is allowed only
while the issue status is `assigned`; the previous row receives an
`unassigned_at` value and a new active row is created for the same assignment
with the new contractor. Reassignment to the current contractor is rejected.
Reassignment does not require a reason. Contractors can access issue details
only through their current allocations.

### `assignments` (planned)

Stores maintenance work packages that group issues.

Fields: `id` (PK), `title`, `instructions` (nullable), `assigned_by` (FK →
`users.id`), and timestamps.

The current database does not yet contain this table or the `assignment_id`
column. They will be introduced through migrations. The migration plan is to
create `assignments`, add `assignment_id` to `issue_assignments`, create one
legacy assignment per issue with existing allocation rows, link that issue's
allocation history to it, and then require the foreign key for all allocation
rows.

An assignment's current issues and contractors are derived from allocations
where `unassigned_at IS NULL`. An assignment with no current issues remains
available to Admins. Contractors cannot be added independently; they are
involved only while they have at least one current issue in the assignment.
Admins can edit the title and instructions; edits overwrite the current
values. Assignment edit history is deferred.

### `issue_status_history`

Stores issue-specific history.

Important fields: - `id` --- PK - `issue_id` --- FK → `issues.id` -
`changed_by` --- FK → `users.id` - `old_status` - `new_status` -
`message` --- nullable - `changed_at`

A status update may contain an optional message. This is not a chat
system.

### `ai_analyses`

Reserved for AI processing.

Important fields: - `id` --- PK - `issue_id` --- FK → `issues.id` -
`predicted_severity` - `confidence` - `model_version` - `status` -
`analyzed_at` - timestamps

### `audit_logs`

Stores important system-wide administrative actions.

Important fields: - `id` --- PK - `user_id` --- FK → `users.id` -
`action` - `entity_type` - `entity_id` - `description` or relevant
data - `created_at`

Examples: - User created - User deactivated/reactivated - Role changed -
Super privilege changed

Audit logs are internal records and are not currently displayed as a
normal UI feature.

## 3. Relationships

``` text
roles 1 ─── * users

users 1 ─── * issues (as reporter)
users 1 ─── * assignments (as creator)
users 1 ─── * issue_assignments (as contractor or assigner)
users 1 ─── * issue_status_history
users 1 ─── * audit_logs

assignments 1 ─── * issue_assignments
issues 1 ─── * issue_assignments
issues 1 ─── * issue_status_history
issues 1 ─── * ai_analyses
```

## 4. Rules

-   An issue has only one current allocation and belongs to one assignment at a time.
-   Reassignment preserves previous assignment history.
-   Reassignment keeps the issue in the same assignment and is allowed only
    while its status is `assigned`.
-   Contractors see the roster for assignments in which they are involved,
    but can open details only for issues currently allocated to them.
-   The assignment contractor list is derived from its current issue allocations.
-   Creating an assignment includes only `reported` issues with no current allocation.
-   Coordinates are authoritative for location.
-   The geocoded address is nullable until reverse geocoding is implemented;
  `address_text` stores an optional manually entered location.
-   Historical records remain when a user is deactivated.
-   Database changes use Laravel migrations.
